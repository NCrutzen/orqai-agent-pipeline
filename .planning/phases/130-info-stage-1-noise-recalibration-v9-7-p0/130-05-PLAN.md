<architectural_directive>
READ THIS FIRST. The operator directive supersedes the prior plan's framing.

The prior version of this plan scoped the carve-out to info-routing via an info-routing-only flag (`stage1_actionable_carveout`) and put the predicate in `web/lib/info-routing/`. That framing is **WRONG** under the new directive. Stage 1 is a cross-swarm architecture (see Skill `spike-findings-agent-workforce`: *"No new Stage 1 code path for info-routing… if you find yourself wanting to special-case info-routing in the worker code, the cross-swarm architecture is leaking — fix it upstream"*). A noise/block rule written for one swarm must live in a **shared pool** and be **adoptable** by any swarm.

This plan therefore:
- Relocates the predicate to a swarm-neutral path (`web/lib/stage-1/actionable-tokens.ts`).
- Replaces the info-routing-only boolean with a swarm-agnostic **adoption pool**: `swarms.stage1_shared_block_rules text[]` — the set of shared Stage-1 block-rule keys this swarm has adopted. Membership of `'actionable_token'` enables the carve-out. Empty array (the default for every existing swarm) = no adoption = no behaviour change.
- The worker gate is a swarm-agnostic membership check (`includes('actionable_token')`), never a `swarm_type ===` literal.

This is the same "registry as source of truth" + "no per-swarm if-branch in classifier code" principle the codebase already enforces for `swarm_noise_categories` and `swarm_intents` (CLAUDE.md, stage-1-regex.md §source-of-truth invariant).
</architectural_directive>

<registry_mechanism_decision>
**Chosen: `swarms.stage1_shared_block_rules text[]` (adopted-rule-keys array), NOT a boolean adopted-flag.**

Both shapes keep existing swarms behaviour-neutral by default and both flow through `loadSwarm`'s `select("*")` with no codegen. The deciding factor is the operator directive itself:

- A boolean named after one rule (`stage1_actionable_carveout`) re-couples the column to a single rule. Adding a second shared block-rule would need another column + migration + type field — which contradicts "a rule written once lives in a shared POOL." The boolean encodes *info-routing adopts THE actionable carve-out*, not *this swarm adopts THESE shared rules*.
- A `text[]` of adopted rule keys is the minimal data shape that actually models "shared pool with per-swarm opt-in adoption." It costs the **same single migration**, the same one `SwarmRow` field, and the same zero codegen. `['actionable_token']` today; another swarm could adopt `['actionable_token', 'payment_admittance_strict', …]` tomorrow with a pure registry UPDATE — no schema change.
- The spike skill's open question (*"Does `generic_noreply_notification` ship info-routing-only or get promoted cross-swarm?"*) shows multiple cross-swarm shared rules are already anticipated. The array is future-proof for that without being over-engineered — it is still ONE column, ONE default (`'{}'`), ONE gate helper.

This is not over-engineering for one rule: it is the correct shape for the directive, at identical migration cost to the boolean.

**Codegen: NONE.** Per stage-1-regex.md §"source-of-truth invariant" + CLAUDE.md Phase 69 note, `npm run codegen` (`gen-intent-types.ts`) reads `swarm_intents` (Stage 3) ONLY; there is no `swarms.*.generated.ts`. `loadSwarm` does `select("*")`, so a new `text[]` column reaches `swarmRow` at runtime automatically (same path the existing `tenant_domains: string[]` column already uses). The only TS change is adding the optional field to the `SwarmRow` interface. Re-confirmed for the array shape: a `text[]` flows via `select("*")` exactly like `tenant_domains` does. Do NOT run codegen; do NOT hand-edit any `*.generated.ts`.
</registry_mechanism_decision>
