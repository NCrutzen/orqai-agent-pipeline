<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email/attachment text → intent agent | Untrusted inbound content (incl. vision-transcribed attachment text) flows into the LLM prompt via assembled_input |
| Orq API ← invoke wrapper | ORQ_API_KEY (Bearer) crosses to the sanctioned Orq Router |
| LLM response → terminal verdict | Model output crosses into the pipeline as a routable decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Tampering | prompt injection via email/attachment text into invoke-intent | mitigate | Attachment text arrives already wrapped in the UNTRUSTED_ATTACHMENT fence (extract.ts) and the Stage 2 fold-in adds an untrusted-data delimiter; the sales agent does pure classification (no tools, no auto-action), output is Zod-enum-gated so injected free text cannot become a routable intent. |
| T-113-02 | Spoofing/Info-disclosure | ORQ_API_KEY handling | mitigate | Key read from `process.env.ORQ_API_KEY` only; never logged; thrown error on missing key does not echo the value. No direct provider key (CLAUDE.md hard rule). |
| T-113-05 | Tampering | out-of-enum / noise-key leakage breaking the 3-way invariant | mitigate | Client Zod `z.enum(SALES_INTENT)` gate is the residual defense behind the server strict json_schema (Plan 02); a value outside the seeded enum throws (surfaces to Bulk Review, never routes). |
</threat_model>
