# Phase 112.5 Plan 05: Activate the category_edited signal via the Phase 117 baseline Summary

One-liner: closes 112.5 SC-2's "her-classificatie via categorie-wijziging" (OUTLOOK-BEHAV-05) by feeding the per-message baseline that Phase 117 persists (`public.swarm_written_categories`) into the dormant `category_edited` path — the worker now SELECTs the last `AI:`-category our system wrote, keys it by `immutable_id`, hands it to `extractTransitions`, and `signal-derive` maps an operator's edit into a labelled `reclassify` row in `swarm_review_signals` (should-be-intent in `category_key`, or `null` for a removed/ambiguous label), fail-safe when no baseline exists, idempotent via the existing dedupe_key 23505 no-op, with zero per-swarm branches.

## Wat is gebouwd

**Task 1 — AI-prefix-aware category_edited verdict in signal-derive** — commit `3cf15049`
- New pure helper `intentKeyFromCategories(categories)`: finds the FIRST entry starting with `AI_CATEGORY_PREFIX` (imported from `@/lib/outlook/intent-category`), returns it prefix-stripped (`entry.slice(AI_CATEGORY_PREFIX.length)`); returns `null` when no AI: entry (covers both removed-label and changed-to-non-AI = ambiguous). No DB, no clock.
- Replaced the flat `category_key = tr.categories?.[0] ?? null` with `intentKeyFromCategories(tr.categories)` in `deriveSignals`.
- `verdictFor(category_edited)` still returns `"reclassify"` — the three operator-edit shapes share one verdict; only `category_key` discriminates. **SignalVerdict union UNCHANGED** (7 members, byte-identical).
- Tests (RED→GREEN): removed-label `[]` → reclassify+null; changed-to-AI `["AI: order_status"]` → reclassify+`"order_status"`; changed-to-non-AI `["Belangrijk"]` → reclassify+null; mixed `["Belangrijk","AI: quote_request"]` → reclassify+`"quote_request"`; multiple AI: → first entry's intent; plus an updated Test 3 (non-AI user-label → null) and the restore+ledger-hit regression assertion (→ correctie_false_positive) still green.

**Task 2 — Seed prevCategories from the swarm_written_categories baseline in the worker** — commit `dd3447c3`
- Inside the existing `derive-and-write-${swarmType}` step.run, AFTER `immutableToEmailId` is built (step 5a):
  1. Invert `immutableToEmailId` → `emailIdToImmutable` (email_id → immutable_id for the resolved set).
  2. `resolvedEmailIds = Array.from(immutableToEmailId.values())`.
  3. Chunked over `ID_CHUNK`: `admin.from("swarm_written_categories").select("email_id, ai_category").eq("swarm_type", swarmType).in("email_id", chunk)` — public schema, admin/service_role read. For each row with a non-null `ai_category`, look up the immutable_id via `emailIdToImmutable`; if found, `prevCategories.set(immutable_id, [row.ai_category])`.
- `prevCategories` is now populated from the baseline (was the empty `new Map<string, string[]>()` of Plan 04). `extractTransitions` already receives it — signature unchanged.
- `prevIsRead` kept empty (read_aged stays dormant — explicitly out of scope). No `if (swarm_type === ...)` branch — `swarmType` comes from the iterated row.
- Tests (RED→GREEN) on the table-aware stateful supabase mock (added a `swarm_written_categories` table + a category-edit-driving delta event): (7) AI: quote_request → AI: order_status → one reclassify row, category_key `"order_status"`, swarm_type `'sales-email'`; (8) removed label `[]` → reclassify, category_key `null`; (9) no baseline row → no reclassify (fail-safe); (10) re-tick same edit → no second row (forced 23505 no-op swallowed).

No new security-relevant surface outside the plan's `<threat_model>`. The worker only adds a read-only SELECT on the Phase-117-owned `public.swarm_written_categories` (never writes it). Register dispositions held:

- **T-112.5-SC (npm/pip installs):** mitigated — no new packages (reuses the supabase admin client + the existing `AI_CATEGORY_PREFIX` constant).
