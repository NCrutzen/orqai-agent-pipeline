## Summary

Deze fase bouwt een **passieve feedback-loop**: een cron-driven Inngest-worker doet per-folder Microsoft Graph delta-sync op `verkoop@smeba.nl`, vangt mail-transities (move/read/category/reply), destilleert daaruit review-verdicts (approve/reject/correctie) en schrijft die in een query-bare tabel die de bestaande Wilson-kalibratie (`web/lib/classifier/wilson.ts`, `PROMOTE_CI_LO_MIN=0.92`) kan voeden. De eerste deliverable is een **folder-conventie-analyse** over de ~1900 historische sales-rijen die de signaal-weging onderbouwt.

**De drie hardste unknowns zijn definitief beantwoord (HIGH confidence):**
1. **Delta is per-folder** (geen mailbox-brede message-delta). Cross-folder moves tracken = delta draaien op meerdere folders en de `@removed reason:deleted` (verdwijning uit oude folder) + verschijning in nieuwe folder samenvoegen op immutable id. [CITED: learn.microsoft.com/graph/delta-query-messages]
2. **Immutable ids werken mét delta** — officieel ondersteund via `Prefer: IdType="ImmutableId"`; nextLink/deltaLink zijn id-format-agnostisch (geen re-sync nodig). [CITED: learn.microsoft.com/graph/outlook-immutable-id]
3. **Category-change + read-state surfacen in delta** als `updated`-events; delta levert óók events die niet aan het `$filter` voldoen (read/unread, `@removed`) omdat tracking op collection-niveau zit. [CITED: learn.microsoft.com/graph/api/message-delta]

**Primary recommendation:** Eén append-only `sales_email_transitions`-tabel (ruwe transitie-events) + een afgeleide `sales_review_signals`-view/tabel (verdict per email_id). Per-folder delta met persistente tokens in een aparte `outlook_delta_tokens`-tabel, 410-Gone → full resync + bootstrap-suppressie (geen signalen voor pre-existing state). Hergebruik `graphFetch` (Zapier-relay), de business-hours cron-conventie, en de Phase-65 replay-id-regel. **Schrijf NOOIT naar `pipeline_events`** voor deze signalen — de partial unique index `pipeline_events_one_per_stage_email (email_id, swarm_type, stage) WHERE override IS NULL` botst; gebruik een eigen tabel (operator-overrides zijn de enige append-second-row uitzondering en die zijn `override IS NOT NULL`).

### Pattern 1: Per-folder delta met persistente token + bootstrap-suppressie
**What:** Elke getrackte folder heeft een eigen delta-token-rij. Eerste run = volledige enumeratie (geen token) → token opslaan, **maar geen signalen emitten** (pre-existing state is geen transitie). Vervolgens: delta-token → alleen changes.
**When to use:** Altijd voor SC-1. De initial-sync teruggeeft ALLE messages in de folder; die mogen niet als "self-archived nu" gelezen worden.
**Example:**
```typescript
// Source: learn.microsoft.com/graph/delta-query-messages (initial sync returns all)
// Bootstrap: first call has no token → store deltaLink, mark bootstrapped=true, emit 0 signals.
const tokenRow = await loadDeltaToken(admin, folderId); // null on first run
let url = tokenRow?.delta_link
  ?? `/users/${enc(mailbox)}/mailFolders/${enc(folderId)}/messages/delta`
     + `?$select=id,subject,isRead,categories,parentFolderId,conversationId,receivedDateTime`;
const isBootstrap = !tokenRow;
let deltaLink: string | null = null;
const events: RawDeltaEvent[] = [];
while (url) {
  const res = await graphFetch(url, { method: "GET", prefer: 'IdType="ImmutableId"' });
  const data = await res.json();
  events.push(...data.value);
  url = data["@odata.nextLink"] ?? null;
  deltaLink = data["@odata.deltaLink"] ?? deltaLink;
}
// persist deltaLink for next round (inside step.run)
await upsertDeltaToken(admin, folderId, deltaLink, /*bootstrapped*/ true);
if (isBootstrap) return; // suppress signal emission on first sync
```
> NB: `graphFetch` in `client.ts` ondersteunt nu géén `Prefer`-header. **Plan-taak:** breid `graphFetch` uit met een optionele `prefer`-parameter (additive, niet-breaking) — andere callers blijven werken.

### Pattern 2: Cross-folder move = correlatie op immutable id
**What:** Een move levert in de BRON-folder een `@removed: {reason:"deleted"}` event en in de DOEL-folder een normaal (created/updated) event met dezelfde immutable id. Correleer over folders binnen één sync-run.
**When to use:** moved-to-afgehandeld, self-archived, restored-from-archive.
**Example:**
```typescript
// Source: learn.microsoft.com/graph/api/message-delta (@removed reason:deleted on move-out)
// id is immutable → stable across the move (Prefer header set).
const leftFolders = new Map<string, string>();   // id → fromFolderId (@removed)
const enteredFolders = new Map<string, string>(); // id → toFolderId (appeared)
for (const ev of allEventsAcrossFolders) {
  if (ev["@removed"]?.reason === "deleted") leftFolders.set(ev.id, ev._folderId);
  else enteredFolders.set(ev.id, ev.parentFolderId ?? ev._folderId);
}
for (const [id, to] of enteredFolders) {
  const from = leftFolders.get(id);
  if (from && bucket(to) === "afgehandeld" && bucket(from) === "inbox")
    emit({ id, kind: "moved_to_afgehandeld", from, to });
  if (from && bucket(from) === "archive" && bucket(to) === "inbox")
    emit({ id, kind: "restored_from_archive", from, to }); // candidate correctie
}
```
> **Caveat (MEDIUM):** als bron- en doel-folder in DEZELFDE sync-tick veranderen ben je veilig; gebeurt de move tussen twee ticks dan zie je alleen het doel-event (created in afgehandeld) en het bron-`@removed` in dezelfde of een vroegere tick. Persisteer de laatst-bekende folder per email_id (in `emails` of een zij-tabel) zodat een move ook detecteerbaar is als de twee helften over ticks gesplitst zijn.

### Pattern 3: restore-from-archive = false-positive-correctie (sterkste signaal)
**What:** Een mail die ÓNS systeem archiveerde (stage-4 ledger `decision='auto_archived_noise'`) en die nu uit Archief terug-in-inbox verschijnt = bewezen false positive.
**When to use:** SC-2 kern-signaal. (Operator deed dit 2× tijdens het 112-canary-incident — het archetype.)
**Example:**
```typescript
// join restored_from_archive transitions against pipeline_events stage=4 ledger
const ours = new Set(
  (await admin.from("pipeline_events").select("email_id")
     .eq("swarm_type", "sales-email").eq("stage", 4)

for (const t of restoredTransitions)
  emitSignal({ email_id: t.email_id,

```

### Pattern 4: reply-detectie via Sent Items + conversationId
**What:** Delta op de Sent Items folder; voor elk verzonden bericht join `conversationId` tegen `emails.conversation_id` (kolom bestaat). Multi-user: `from`/`sender` op het sent-bericht attribueert wie antwoordde.
**When to use:** "replied"-transitie. `$select=conversationId,from,sender,sentDateTime,internetMessageId`.
**Caveat (MEDIUM):** shared mailbox — een reply kan via een persoonlijk account verzonden zijn (niet in verkoop@-Sent). Dan mis je 'm. Documenteer als bekende ondergrens; reply is een approve-achtig signaal, false-negatives zijn acceptabel.

## Common Pitfalls

### Pitfall 1: Delta levert events die niet aan je $filter voldoen
**What goes wrong:** Je filtert op `receivedDateTime ge X` maar krijgt toch `@removed` + read-state events terug.
**Why it happens:** Delta tracking is collection-level, niet message-level — read/unread en move-out worden altijd geëmit. [CITED: learn.microsoft.com/graph/api/message-delta]
**How to avoid:** Verwacht en handel `@removed`-entries expliciet af; gebruik `$filter` alleen om de *initial* corpus te begrenzen, niet als garantie.
**Warning signs:** Onverwachte `@removed`-rijen, dubbele isRead-events.

### Pitfall 2: 410 Gone / resyncRequired bij verlopen of geïnvalideerd token
**What goes wrong:** Delta-call faalt met 410 → worker crasht of mist changes.
**Why it happens:** Delta-tokens verlopen (Exchange houdt ze beperkte tijd); ook na mailbox-moves.
**How to avoid:** Vang 410 (body `code: "resyncRequired"` of `SyncStateNotFound`) → gooi token weg, doe full resync, **maar suppress signal-emit** (zelfde als bootstrap) of diff tegen laatst-bekende folder-state om echte transities te behouden. Documenteer welke variant gekozen wordt.
**Warning signs:** HTTP 410 in relay-logs; gat in transitie-stroom.

### Pitfall 3: Cross-folder move gesplitst over twee ticks
**What goes wrong:** Je ziet alleen "verschenen in afgehandeld" of alleen "@removed uit inbox", niet beide → move niet herkend.
**Why it happens:** Move gebeurt tussen twee delta-ticks; bron-event in tick N, doel-event in tick N+1.
**How to avoid:** Persisteer laatst-bekende folder/bucket per email_id; een verschijning in folder Y waar de opgeslagen folder X was = move X→Y, ook zonder gelijktijdig `@removed`.
**Warning signs:** Veel "entered afgehandeld" zonder bijbehorend "left inbox".

### Pitfall 4: Inngest 60s step-timeout op grote folders
**What goes wrong:** Een folder met duizenden messages in initial sync overschrijdt de 60s gateway in één step.
**Why it happens:** Bootstrap enumereert alles; paginatie kost veel sequentiële relay-calls.
**How to avoid:** Per-folder per-page step-grenzen (zoals 112 backfill BATCH_SIZE=150), `Prefer: odata.maxpagesize`; persisteer skipToken tussen steps zodat een step één pagina-batch doet. Ids-only over step-boundaries (112: full candidates overschreden step-output-limit).
**Warning signs:** Step-timeout failures op de eerste run.

### Pitfall 5: Restore-detectie zonder ledger-join = false correctie
**What goes wrong:** Elke restore-from-archive geteld als correctie, ook handmatige team-restores van eigen mail.
**Why it happens:** Niet elke restore is een correctie van ÓNS systeem.
**How to avoid:** Join tegen `pipeline_events` stage=4 `auto_archived_noise`; alleen restores van door-ons-gearchiveerde mail = `correctie_false_positive`. [VERIFIED: 112-03-SUMMARY ledger als her-archiveer-bescherming]
**Warning signs:** Correctie-rate onrealistisch hoog.

async function graphFetch(
  path: string,
  options: { method: string; body?: unknown; prefer?: string } = { method: "GET" },

## Open Questions

1. **Levert delta een `parentFolderId` op het message-object?**
   - Wat we weten: `$select=parentFolderId` is een geldig message-veld; delta ondersteunt `$select`.
   - Wat onduidelijk is: of `parentFolderId` betrouwbaar gevuld is in delta-responses (vs. alleen folder-context uit de delta-URL zelf).
   - Aanbeveling: bevestig in eerste smoke; fallback = folder-context = de folder waarop de delta-call draait (dat is hoe per-folder delta werkt — de folder is impliciet bekend).

2. **Welke folders trackt de delta-worker actief?**
   - Wat we weten: per-folder delta; meer folders = meer calls. Relevante buckets: inbox, archive, elke afgehandeld-{jaar}, Sent Items (voor reply).
   - Wat onduidelijk is: of óók Junk/DeletedItems getrackt moeten worden.
   - Aanbeveling: start met inbox + archive + afgehandeld-* + Sent Items; folder-map registry maakt uitbreiden een insert.

3. **Hoe consumeert Wilson exact deze rows?** (D-05 downstream)
   - Wat we weten: `wilsonCiLower(n,k)`, `shouldPromote`. De promotion-cron leest vandaag `pipeline_events.override`.
   - Wat onduidelijk is: of de nieuwe verdict-tabel een view/adapter naar dezelfde n/k-vorm nodig heeft, of dat een aparte consument gebouwd wordt (waarschijnlijk V10.0 self-learning — buiten scope).
   - Aanbeveling: lever de verdict-tabel query-baar op (per category_key: approve/reject counts); de feitelijke Wilson-koppeling kan een dunne adapter zijn of expliciet deferred naar V10.0. Bevestig scope met operator/planner.
