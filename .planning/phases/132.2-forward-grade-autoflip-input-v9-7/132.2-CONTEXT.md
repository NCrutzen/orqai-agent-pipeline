**Approach:** Option A — feed main's autoflip (operator-decided, seed

## The gap (why this phase exists)

The autoflip ARMS live Outlook forwarding by releasing per-bucket
`stage_4_forward_buckets[x]=true`, but it grades on a **proxy**:
`swarm_review_signals.transition_kind="category_edited"` (operator edited the AI's
Outlook label) graded **per-mailbox** via `planForwardBucketFlips`. The operator's
real ground truth — where mail was **actually forwarded** (memory
`forward-match-as-wilson-ground-truth`) — exists only in the one-shot
`forward-wilson-backfill.ts`. There is no ongoing capture, and the per-mailbox
proxy is a weaker signal than the per-bucket forward-match Wilson grade.

## Reconciliation (the design call the seed left open)

Option A as worded ("keep `planForwardBucketFlips`") is in tension with the
forward-Wilson grade: the current path grades **per-mailbox** (`gradeVerdict` /
`MATCH_RATE_GATE` 0.85 over `category_edited`); forward-Wilson grades **per-bucket**
(`gradeBucketsByWilson` keyed by predicted bucket). They cannot both literally
hold. Honest reconciliation, kept minimal:

- **Graft** the per-bucket grade+release core (from the record branch's standalone
  worker) **into the existing autoflip cron**, and **retire** the per-mailbox
  `category_edited` path (`computePerMailboxStats` / `planForwardBucketFlips` /
  `buildShadowRows` / `buildCategoryToBucket`).
- **Keep** the cron shell (id, `concurrency:[{limit:1}]`, `retries:1`, triggers),
  the **idempotent release-only `||` merge** of `stage_4_forward_buckets`, the
  **panic lever** (migration `20260624b…revert`), and the **regression alert**
  (adapted from per-mailbox precision-drop to per-bucket Wilson-drop).
- **Brand/mailbox reachability becomes implicit** — a bucket only accumulates
  forward observations from the mailboxes that actually forward to it. The
  per-bucket false-success guard is now `MIN_OBSERVED_N=20` + the coverage gate,
  which is tighter and more direct than the per-mailbox `MIN_GRADED_N` proxy.

**Why this is still smaller than the stale standalone cron:** no new Inngest
function, no orchestrator/worker fan-out, no `forward_grade_config` column, no
`events.ts` additions, no `route.ts` change. Just: one `jsonb` column + three
cherry-picked pure helpers + the union members + an autoflip rewrite + tests.

## The three open points — RESOLVED

### 1. Slot/milestone → **V9.7.x, Phase 132.2** (operator-decided)
Attached to the V9.7 forward gate it modifies; reopens V9.7 like 88.1 / 132.1
precedent. Feeds V10.0 as a side-benefit.

### 2. Capture-scheduling → **fold into the autoflip cron as a daily-gated step** (engineering call)
Rides the existing autoflip cadence (seed point 4: "no separate standalone grade
cron"). The **release** evaluation runs every 30 min off the **accumulated
ledger**; the **Graph Sent-Items scan** runs **at most once/day** (ledger-gate:
skip if a `forward_observed*` row already has `created_at >= date_trunc('day',
now())`). Rationale: forward ground truth changes slowly, and the Graph path is
the single hardcoded Zapier connection (memory
`outlook-connection-id-hardcoded-ingest-spof`) — don't load that SPOF 28×/day for
daily data.
- *Rejected:* every-tick scan (28 redundant Graph scans/day); a separate thin
  daily capture function (extra function for no gain — the autoflip already runs
  and already owns the release merge).
- *Known ceiling (ponytail):* on a rare day with **zero** info@ forwards the
  ledger-gate finds no today-row and re-scans each tick. Acceptable (info@ sees
  ~300 mail/mo); upgrade to a `settings` heartbeat only if it ever bites.

### 3. Signal-shape → **take the cherry-picks as-is; persist `observed_meta` in a new `jsonb` column; keep the 0.70 gate** (engineering call)
- **Cherry-pick as-is:** `forward-signal.ts` (`buildForwardSignalRow` +
  deterministic `dedupe_key`); the `forward_observed` + `forward_observed_no_verdict`
  union members in `signal-derive.ts` **and** `transition-extract.ts` (needed for
  `buildForwardSignalRow`'s `Extract<SignalVerdict,…>`; also gives cross-swarm
  dedupe isolation + keeps an exhaustive `TransitionKind` switch from silently
  ignoring forward rows); `computeBucketCoverage` + `FORWARD_COVERAGE_GATE=0.7` in
  `forward-wilson.ts`.
- **Keep `forward_observed_no_verdict`:** near-zero cost, gives a complete forward
  ledger for V10.0 (a forward we couldn't grade is itself a signal). Never fed to
  Wilson or coverage (predicted_bucket null).
- **Gate stays `FORWARD_WILSON_GATE=0.70`** — do **NOT** take the record branch's
  0.85 bump (operator decision 2026-06-25; internal dept forwarding is low-stakes
  and reversible).
- **`observed_meta` home — the one schema change.** `swarm_review_signals` has
  `category_key` (→ predicted bucket) and `mailbox` (→ source) but **no column for
  the observed bucket**, which grading must read back from the accumulated ledger.
  The record branch overloaded `transition_kind` with a JSON blob — rejected (that
  column is read as a literal kind by signal-derive / behavior-sync /
  intent-label). Instead add a **nullable `observed_meta jsonb`** column (table is
  already RLS-enabled with a `service_role` ALL policy → no new policy; no codegen
  — DB types aren't codegen-tracked here). `buildForwardSignalRow` already returns
  `observed_meta`; the cron inserts it into the column directly.

## Why the stale branch's grade was wrong (the bug we must not reproduce)
The record worker built its graded `observations[]` only from **new (non-dedup)**
forwards each tick and graded in-memory — so Wilson `n` never accumulates across
ticks and a bucket could never reach `n≥20`. **Fix:** grading reads the
**persisted ledger** (all `forward_observed` rows for the swarm) and reconstructs
`ForwardObservation[]` from `category_key` (predicted) + `observed_meta`
(observed) + `mailbox` (source). Capture writes the ledger; grade reads it back.
