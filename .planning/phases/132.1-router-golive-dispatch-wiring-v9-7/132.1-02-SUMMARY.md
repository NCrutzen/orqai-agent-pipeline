# Phase 132.1 Plan 02: Routing Master-Category Colour Provisioning Summary

`ensureRoutingMasterCategories(mailbox, buckets)` idempotently provisions ONE distinct non-grey Outlook preset colour (`preset5`) for every routing master category via Graph `masterCategories`, so operators distinguish routing labels from the grey `AI:` intent labels at a glance — names sourced from `buildRoutingCategory` (single vocabulary source), grey intent labels left untouched.

## What Was Built

- **`ROUTING_CATEGORY_PRESET_COLOR = "preset5"`** in `web/lib/outlook/client.ts` — the one chosen non-grey swatch. Outlook category colours are `preset0`..`preset24`; `preset0` is the grey "no colour" default that `AI:` INTENT labels keep. Routing labels get `preset5` (NOT per-bucket, NOT per-brand) per D-03.
- **`ensureRoutingMasterCategories(mailbox, buckets)`** — idempotent provisioning:
  - GET `/users/{mailbox}/outlook/masterCategories`, zod-parse, build a `Set` of present `displayName`s.
  - Desired routing display names sourced from `buildRoutingCategory` (NEVER duplicated literals): static `triage`/`algemeen` + per-bucket `held`/`forwarded`/`dedup` variants. De-duped defensively.
  - POST only the MISSING names, each with `preset5`. A second call POSTs nothing (idempotent).
  - Additive only — never PATCHes/deletes existing categories, never touches the grey `AI:` intent labels (threat T-132.1-05 idempotency / T-132.1-06 no-clobber).
  - Routes through the single `graphFetch` credential boundary + its built-in 504/socket retry.
- **6 mocked-`graphFetch` tests** (GET/POST-aware mock harness added to the existing suite): non-grey preset assertion, full provisioning with same preset, exact `buildRoutingCategory` name match, idempotency = 0 POSTs, partial-existing = only-missing POSTed, never-POSTs/recolours the grey intent label.
