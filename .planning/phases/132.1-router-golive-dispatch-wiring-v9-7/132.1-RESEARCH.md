## Summary

Phase 131 built the entire info-routing router (destination registry, `info-routing-coordinator` Orq agent, 6-field verdict, two-layer dedup, ROUTE-08 shadow harness) and Phase 132 built the Stage-4 forward worker (idempotent, dry-run-gated, brand-aware) + `AI: routed →` category stamp-back. Both are wired, tested, and held behind `dry_run_config.stage_3_routing=true` / `stage_4_forward_buckets={}`. **Nothing in this phase is greenfield — it is a wiring fix + three flag activations + reuse of the existing shadow harness.**

The dispatch bug is fully root-caused (two debug docs + the revert migration `20260623c`). The `email_id=null` createRun crash is NOT a code bug in any single producer — it is a **registry-shape mismatch**: info-routing's `swarm_noise_categories.unknown.swarm_dispatch` was pointed directly at `pipeline/coordinator.requested`, but the only payload the verdict-worker carries to that event is `{automation_run_id, swarm_type, category_key, message_id, source_mailbox}` — **no `email_id`** (email_id resolution is normally Stage 2's job, and info-routing has `stage2_entity_resolver=NULL` by design). The coordinator reads `event.data.email_id` and `createRun` INSERTs it into a NOT-NULL column → crash. The structural fix is to make the coordinator (or an interposed step) **resolve `email_id` from `message_id`** the same way Stage-2's resolver already does — info-routing is a deliberate no-Stage-2 swarm, so it needs a one-step email_id resolution that Stage 2 would otherwise perform.

A second, higher-risk finding for D-01: the `AI: routed →` category is stamped **only inside the forward worker**, which only runs when a bucket is RELEASED (live forward). During the shadow/dry-run window — exactly when ground-truth must be measured — **no routing category is stamped and `swarm_written_categories` (the 112.5 baseline) is never seeded**, so the operator has nothing to correct and the delta-sync has no baseline to diff against. The chicken-and-egg must be broken: a held verdict must still stamp a routing category (e.g. `AI: held → <bucket>`) and write the baseline, so operator corrections become measurable BEFORE any forward fires.

**Primary recommendation:** (1) Resolve `email_id` from `message_id` in the coordinator entry (reuse the Stage-2 resolver's `.or(source_id.eq.X,internet_message_id.eq.X)` pattern), gated to the no-Stage-2 routing path; re-apply the `swarm_dispatch` flip as a migration. (2) Move/duplicate the routing category-stamp + `swarm_written_categories` baseline write into the HELD path so shadow ground-truth is captured during dry-run. (3) Add a `masterCategories` `presetColor` ensure-call in `web/lib/outlook/client.ts`. (4) Reuse the ROUTE-08 harness unchanged; wire its `human_category` read (the one TODO it documents) and add a per-mailbox auto-flip cron that patches `stage_4_forward_buckets` when `gradeVerdict` passes with `graded_n ≥ MIN_GRADED_N`.

### Recommended structural fix (for the planner — Claude's Discretion item)

The debug doc lists three options. The CONTEXT goal ("reach the coordinator with a valid `email_id` while cleanly skipping Stage 2") maps to **Option B + Option C combined**:

- **Resolve email_id from message_id inside the coordinator entry** (Option C), gated to the no-Stage-2 routing path: when `event.data.email_id` is absent, load the emails row by `source_id`/`internet_message_id` (reuse the Stage-2 resolver's `.or(...)` query) inside a `step.run`, then proceed. This is the swarm-agnostic guard the revert migration header itself names as the intended V9.7 wiring: *"an `info-routing-coordinator` that resolves `email_id` from `message_id` since there is no Stage 2."*
- **Re-apply the dispatch flip as a migration** (Option B/A reversal): set `swarm_noise_categories(info-routing,'unknown')` back to `action='swarm_dispatch', swarm_dispatch='pipeline/coordinator.requested'` — but ONLY once the email_id resolution lands, so the flip no longer crashes. Persist as a migration (the prior state was an undocumented live edit — CLAUDE.md registry-as-migration rule).

**Why resolve in the coordinator, not in the verdict-worker:** the verdict-worker's payload is shared across all swarms and deliberately carries no `email_id` (SWARM-02; email_id is Stage-2's contract). Threading email_id through the verdict-worker for one swarm would either special-case it (forbidden `if swarm_type` branch) or force a DB read into a worker that is meant to be Stage-2-agnostic. Resolving inside the coordinator (which already owns the `createRun` that needs it) keeps the fix swarm-agnostic: debtor/sales arrive WITH `email_id` so the resolution `??` branch never runs (byte-neutral), and any future no-Stage-2 swarm is covered for free.

**Replay-safety (CLAUDE.md Inngest rule):** the email_id resolution must live inside a `step.run` (it is a DB read producing a value used as a write key downstream). The coordinator already generates `run_id` inside `step.run("resolve-run-id")` at lines ~250-253 — follow the same boundary.

## Common Pitfalls

### Pitfall 1: Stamping the routing category only on live forward (the D-01 chicken-and-egg) — HIGH RISK
**What goes wrong:** The `AI: routed →` stamp + `swarm_written_categories` baseline write live ONLY in `stage-4-info-routing-forward.ts:183-199`, which runs only when a bucket is RELEASED. During the dry-run/shadow window (before any flip) nothing is stamped, 112.5 has no baseline, and the operator has no AI-category to correct — so **ground-truth precision can never be measured**, and the auto-flip can never trigger. Deadlock.
**Why it happens:** Phase 132 designed the stamp as a forward side-effect; Phase 132.1 needs it as a measurement seed that must precede the forward.
**How to avoid:** In the HELD path of the coordinator routing block (around lines 497-509), stamp `AI: held → <bucket>` (use `mergeRoutingCategory(..., "held", bucket)`) AND call `writeWrittenCategory` to seed the 112.5 baseline. Then the operator's correction of that held label becomes the ground-truth signal.
**Warning signs:** `info-routing-precision-shadow.ts report` keeps returning `insufficient_sample` with `graded_n=0` even after 112.5 is enabled and operators have triaged mail.

### Pitfall 2: Re-flipping the dispatch row before the email_id fix lands
**What goes wrong:** Setting `swarm_dispatch='pipeline/coordinator.requested'` reproduces the exact 24-fail/24h NOT-NULL crash on every real info@ email.
**How to avoid:** Sequence the migration AFTER the email_id resolution code is deployed. The plan must order: (1) email_id resolution code + (2) held-path stamp, THEN (3) the dispatch flip migration, THEN (4) `behavior_tracking` enable, THEN (5) `stage_3_routing=false` only if intent-dispatch is wanted (it is NOT this milestone — the forward emit is independent of the held gate).
**Warning signs:** new `createRun: null value in column "email_id"` rows in `pipeline_events` stage=3 decision=worker_failed.

### Pitfall 3: Auto-flip on a tiny or noisy sample (D-02 minimum-N)
**What goes wrong:** A mailbox reaches "100% precision" on 3 graded emails and auto-releases a live forward on real customer mail.
**How to avoid:** Reuse `gradeVerdict`'s `MIN_GRADED_N` guard (currently 50) PER MAILBOX. The auto-flip cron must require `status='graded' && pass===true` (never `insufficient_sample`, which returns `pass:null`). Recommend a measurement window (see Open Questions) and a per-mailbox `graded_n` denominator, not a swarm-wide one.
**Warning signs:** a bucket flips to released with `graded_n` near the floor; precision regresses after release.

### Pitfall 4: INVERSE polarity confusion between the two gate flags
**What goes wrong:** Writing `stage_4_forward_buckets[bucket]=false` thinking it releases, or reading `stage_3_routing` as released-when-true.
**How to avoid:** `isStage3RoutingGated` → TRUE=held. `isForwardBucketReleased` → requires `=== true` to release (everything else held). They are opposite by design and documented in `dry-run-gate/index.ts:118-128`. The auto-flip writes `true` to RELEASE.

### Pitfall 5: Per-mailbox flip but per-bucket release map
**What goes wrong:** D-02 says smeba and fire-control flip INDEPENDENTLY, but `stage_4_forward_buckets` is keyed by BUCKET, not by mailbox.
**Why it matters:** Precision is measured per mailbox; release is per bucket. A bucket (e.g. `storingen`) maps to a (bucket×brand)→mailbox target. The auto-flip must reconcile "this mailbox's precision cleared" with "release the buckets whose target is reachable from this mailbox's brand."
**How to avoid:** Measure precision per mailbox (group `coordinator_runs` by `source_mailbox`/brand), but release the buckets that the cleared mailbox's mail routes to. The planner must define this mapping explicitly — it is the subtlest part of D-02. (See Open Questions.)

### Pitfall 6: The false-success guard is load-bearing — don't weaken it
**What goes wrong:** Removing/lowering `MIN_GRADED_N` to "get a green light" reintroduces the 100%-over-0-rows trap the harness was specifically built to prevent.
**How to avoid:** Keep `MIN_GRADED_N` and the `insufficient_sample`/`pass:null` contract. The auto-flip must treat `pass:null` as "do not flip."

## Open Questions

1. **Measurement window + per-mailbox minimum-N (Discretion item).**
   - What we know: `MIN_GRADED_N=50` and `MATCH_RATE_GATE=0.85` already exist in the harness. ~663 actionable unknowns/30d across info@ (Phase 131 SPEC); the high-confidence subset is smaller, and graded_n requires an operator correction per email.
   - What's unclear: the calendar window (rolling 14d? since-enable?) and whether 50 graded high-confidence verdicts is achievable per mailbox in a reasonable time.
   - Recommendation: rolling window since `behavior_tracking` enable; per-mailbox `graded_n ≥ 50` AND `overall_match_pct ≥ 0.85` AND `status='graded'`. If 50 is too slow for fire-control (lower volume), the planner may propose a lower per-mailbox floor with operator sign-off — but never below a statistically meaningful N.

2. **Per-mailbox precision → per-bucket release reconciliation (Pitfall 5).**
   - What we know: precision is naturally measured per mailbox/brand; `stage_4_forward_buckets` is keyed by bucket.
   - What's unclear: the exact mapping rule when a bucket's target mailbox spans brands.
   - Recommendation: the auto-flip computes precision grouped by `source_mailbox` (brand), then releases the buckets whose `routing_destinations` rows for that brand cleared. Confirm with operator (A4).

3. **Monitoring/alert + one-flag revert (D-02).**
   - What we know: `dry_run_config.stage_4_forward_buckets` is a jsonb map; setting a bucket back to `false`/removing it is the one-flag revert.
   - Recommendation: alert on (a) new `worker_failed` createRun-null after the flip (regression), (b) forward worker non-ok Graph responses, (c) precision regression below 0.85 post-release. Provide a single migration/SQL one-liner that sets all info-routing forward buckets to `false`.
